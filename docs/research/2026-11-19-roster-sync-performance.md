# Обновление ростеров: исследование производительности — 19.11.2026

Задача: уменьшить время и нагрузку обновления персонажей без потери данных и событий активности. Это результаты исследования, не выложенная оптимизация обработчика.

## Что уже исправлено отдельно

- `a5280fa`: первый цикл обновления игроков ждёт первоначальную загрузку составов вне общей блокировки. Устранён пропуск первого часа после перезапуска.
- `4afceab`: проверка состава использует сохранённую связь playerId → аликод; профиль запрашивается для неизвестных/неполных записей. Имена, роли, время активности берутся из свежего ответа гильдии. На живом TEST после выкладки семь гильдий обработаны за 6,2 с вместо примерно 229–271 с, запросов профиля 0. Полная локальная suite — 490 тестов. Публичный образ не менялся.

Исходный обработчик: [services/activity_diff.py](../../services/activity_diff.py), хранение кэша: [database.py](../../database.py).

## Методика

На действующем VPS, Python 3.11, тот же Comlink. Одинаковые 50 игроков из семи гильдий, 19 735 записей персонажей/кораблей. Схемы/индексы копировались в отдельную временную SQLite; в неё переносился исходный кэш только выбранных игроков. Каждый режим стартовал с одной и той же копии. В рабочую БД эксперимент не писал; Discord-сообщения не отправлялись.

По два прохода каждого режима в прямом и обратном порядке. Все варианты кроме явно указанного `delta ×2` использовали максимум пять одновременных загрузок. Между загрузками сохранена исходная задержка 0,1 с. Общая блокировка тяжёлой синхронизации исключала одновременный запуск других тяжёлых работ бота; ожидание этой блокировки не включено в таблицы. Остальные серверные службы продолжали работать.

Время — длительность обработки всех 50 игроков. CPU — `time.process_time()` экспериментального процесса со всеми его потоками, **без отдельного CPU Comlink и остальных служб**. Для JSON/очереди повторно сверялись число сохранённых строк и полный ростер одного ответа за проход; в опыте с очередью также сверялись датакроны этого ответа. Семантические проверки выполнялись вне измеряемого интервала. Это проверка прототипов, не полный регрессионный набор для готовой реализации.

Ограничения: только два повтора; небольшая временная БД отличается размером/историей от рабочей; GIL, аллокатор и прогрев в последовательных проходах влияют на метрики. Пиковую RSS между режимами нельзя считать независимым сравнением. Замеры нельзя прямо экстраполировать на полный рабочий цикл или складывать проценты разных оптимизаций.

## Профиль исходного обработчика, пять одновременно

50 успешных обновлений, 19,06 с общего времени, 15,75 с CPU. Суммы CPU стадий:

| Стадия | CPU, с |
|---|---:|
| Разбор JSON ответов HTTP | 4,24 |
| Чтение и разбор старого ростера | 5,10 |
| Сериализация и запись нового ростера | 4,08 |
| Запись метаданных | 0,55 |

Стадии частично вложены: полный `_store_roster_diff` включал чтение/запись, его CPU 9,69 с, поэтому его нельзя ещё раз прибавлять к строкам таблицы. Суммы wall-time отдельных вызовов перекрываются между работниками и не равны длительности пакета.

## Опыт 1: разделение загрузки и SQLite

`queue`: пять загрузчиков → ограниченная очередь → один писатель, прежние функции записи. `transaction`: та же очередь, соединение/транзакция на игрока объединены в прототипе; commit/close вложенных помощников отложены до конца операции. `delta`: дополнительно сравниваются декодированные юниты, JSON сериализуется только для изменённых; время проверки обновляется у всех строк. Полный исходный ростер сохраняется для остальных функций приложения.

| Вариант | Время, с | CPU, с |
|---|---:|---:|
| Исходный, ×5 | 21.38 | 18.23 |
| Очередь, ×5 | 22.35 | 19.68 |
| Одна транзакция, ×5 | 22.02 | 19.46 |
| Изменённые строки, ×5 | 19.59 | 17.89 |
| Изменённые строки, ×2 | 20.82 | 15.11 |

500 запросов/обновлений, ошибок 0. В delta сериализовались 14 из 19 735 юнитов, но чтение/разбор старых данных, глубокое сравнение и обновление времён остаются. Выигрыш ×5 около 8% по времени и лишь 2% CPU; паузы цикла обработки в эксперименте выросли. Отдельная очередь и объединённая транзакция в этих прототипах не дали ускорения. Это не доказывает бесполезности всех иных реализаций, но не даёт оснований выкатывать именно их ради скорости.

## Опыт 2: JSON и сжатие HTTP

В отдельном процессе сравнивались стандартный JSON и `orjson 3.13.0` при той же обычной записи ×5. Быстрый декодер заменял `loads` Python-обёртки Comlink и JSON-операции модуля database; сериализация оставалась текстом UTF-8 для SQLite, не BLOB. Рабочие зависимости не менялись: wheel ставился в отдельный `/tmp` каталог, добавленный в sys.path только экспериментального процесса, и удалён после измерений.

| Вариант | Время, с | CPU, с |
|---|---:|---:|
| Стандартный JSON + gzip | 20.34 | 17.49 |
| orjson + gzip | 17.73 | 14.21 |
| Стандартный JSON без gzip | 19.95 | 17.93 |
| orjson без gzip | 16.71 | 14.61 |

400 обновлений, ошибок 0. Быстрый JSON при сохранённом gzip: примерно **−13% времени, −19% CPU** относительно своего контроля. Отключение gzip без замены JSON дало мало по времени и увеличило CPU экспериментального процесса. С быстрым JSON без gzip время немного меньше, но CPU клиента немного выше; CPU Comlink отдельно не измерялся, поэтому общий выигрыш от выключения сжатия не установлен.

Прямой HTTP-пробой на этом сервере: корректный POST `/player` с `Accept-Encoding: gzip` возвращал 200, `Content-Encoding: gzip`, ETag; распакованный профиль одного игрока 3,36 MiB. Повторный POST с `If-None-Match` вернул 200 и полный ответ, а не экономию на передаче/разборе. Наличие ETag само по себе не даёт работающего условного обновления POST. Эти наблюдения относятся к текущей установленной службе.

В служебной строке `BENCH_START` профилировщика/JSON-теста осталось историческое поле `order` исходного скрипта; фактические режимы и порядок записаны в строках `RESULT` (`mode`, `parallel`, `run`). Для анализа использовались именно эти строки.

## Рекомендация

1. Первым небольшим изменением рассматривать быстрый JSON, сохранив gzip и совместимый текстовый формат SQLite. До выкладки нужны регрессии типов/чисел, обработки повреждённого ответа, событий активности и метаданных; не заменять JSON глобально во всём приложении по результатам этого опыта.
2. Для снижения пиков рассмотреть распределение сроков проверки по игрокам: обновлять небольшое число постоянно, сохраняя максимальный возраст данных, вместо общего залпа. Это не уменьшает число запросов за час. Для 338 игроков и периода 10 минут средний темп около одного игрока за 1,8 с. Планировщик должен догонять просроченное после рестарта и не задерживать ручное обновление; такое расписание здесь не включалось и полный цикл с ним не замерялся.
3. Более крупная будущая переработка: отделить время проверки игрока и компактное состояние для диффа активности от больших JSON персонажей. Иначе обновление одного timestamp всё ещё затрагивает строки с большими JSON. Это гипотеза по структуре кода, не измеренный выигрыш; потребуются миграция и согласование с ручным обновлением.
4. Не сокращать проверки по неизменному ГМ или времени входа: это не гарантия неизменных модулей/персонажей. Не обещать, что новый async-клиент или большее число работников автоматически ускорят обработку.

Архив скриптов и сырых результатов на VPS: `/opt/bot/_sync_options_20261119`. Скрипты содержат обращения только к локальному Comlink и временной БД, секретов нет. Код приложения, интервалы и рабочая параллельность этим исследованием не изменялись.

## Первичные источники и ограничения API

### Comlink: уменьшение и разделение запросов

Проверено 19.11.2026 по первичной документации и исходникам. Исследование транспорта, без запросов к игре или рабочему серверу. Версия исходников comlink-python: `796cd33c06c5e2ccf932f3a9d3883d3d50f2d5ca`; она может отличаться от установленного пакета, поэтому перед изменением сверить локальный код.

## Что документировано

- `/player` принимает одного игрока: `allyCode` либо `playerId`, плюс `enums`. Параметров выбора персонажей/полей, страниц, дельты, версии предыдущего снимка или массива игроков в описании этого endpoint нет. Это граница документированного API, а не доказательство невозможности любого недокументированного запроса. [Документация `/player`](https://github.com/swgoh-utils/swgoh-comlink/wiki/Getting-Started#player), [сборка payload](https://github.com/swgoh-utils/comlink-python/blob/796cd33c06c5e2ccf932f3a9d3883d3d50f2d5ca/src/swgoh_comlink/_base.py#L307).
- `requestSegment` и `items` действительно позволяют делить ответ, но относятся к `/data` — статическому справочнику игры. Переносить эти параметры на `/player` оснований нет. [Документация `/data`](https://github.com/swgoh-utils/swgoh-comlink/wiki/Getting-Started#data), [отдельный построитель game-data payload](https://github.com/swgoh-utils/comlink-python/blob/796cd33c06c5e2ccf932f3a9d3883d3d50f2d5ca/src/swgoh_comlink/_base.py#L336).
- `/playerArena` возвращает меньший, но другой набор данных — арены. Это замена полного запроса только для функций, которым ростер не нужен. Для синхронизации персонажей и модулей не подходит. [Описание](https://github.com/swgoh-utils/swgoh-comlink/wiki/Getting-Started#playerarena).
- Условные запросы через `ETag`/`If-None-Match` или `If-Modified-Since`, gzip-сжатие `/player` и возвращение только изменившихся юнитов не описаны в рассмотренной документации. Поддержку сжатия и валидаторов нужно отдельно проверить по реальным заголовкам ответа; отсутствие описания не равно отсутствию поддержки. [Документированные endpoint и параметры](https://github.com/swgoh-utils/swgoh-comlink/wiki/Getting-Started#endpoints).

## Что означает «streaming guild roster»

Примеры `streaming_guild_roster.py` и `streaming_guild_roster_advanced.py` вызывают `/guild`, получают `playerId` участников, затем создают отдельные задачи `get_player` для каждого участника через `asyncio.TaskGroup`. Продвинутая версия добавляет повторы с увеличением задержки, валидацию и обработку ошибок. Это параллельные отдельные полные запросы, а не один пакетный запрос и не разбиение JSON одного игрока на порции. Пример сохраняет результаты задач в памяти до формирования сводки. [Базовый пример](https://github.com/swgoh-utils/comlink-python/blob/796cd33c06c5e2ccf932f3a9d3883d3d50f2d5ca/examples/Async/streaming_guild_roster.py), [продвинутый пример](https://github.com/swgoh-utils/comlink-python/blob/796cd33c06c5e2ccf932f3a9d3883d3d50f2d5ca/examples/Async/streaming_guild_roster_advanced.py).

## Возможности в клиентской обработке

1. **Соединения уже переиспользуются.** Sync создаёт долгоживущий `httpx.Client`, async — `httpx.AsyncClient`; для последнего явно задан `keepalive_expiry=None`. Если приложение уже держит один экземпляр клиента, «добавить keep-alive» само по себе не устраняет новый расход. Нужно избегать создания клиента на каждого игрока. [Sync init](https://github.com/swgoh-utils/comlink-python/blob/796cd33c06c5e2ccf932f3a9d3883d3d50f2d5ca/src/swgoh_comlink/swgoh_comlink.py#L82), [async init](https://github.com/swgoh-utils/comlink-python/blob/796cd33c06c5e2ccf932f3a9d3883d3d50f2d5ca/src/swgoh_comlink/swgoh_comlink_async.py#L77).
2. **Async не делает разбор JSON асинхронным.** В обоих клиентах тело полностью получено до `loads(r.content.decode("utf-8"))`. У async этот синхронный разбор находится в coroutine; простая замена `to_thread(sync_client.get_player)` на async-клиент способна перенести тяжёлый разбор на основной event loop. Это вывод из кода, который нужно измерять, а не обещание ускорения. [Sync decode](https://github.com/swgoh-utils/comlink-python/blob/796cd33c06c5e2ccf932f3a9d3883d3d50f2d5ca/src/swgoh_comlink/swgoh_comlink.py#L197), [async decode](https://github.com/swgoh-utils/comlink-python/blob/796cd33c06c5e2ccf932f3a9d3883d3d50f2d5ca/src/swgoh_comlink/swgoh_comlink_async.py#L195).
3. **Убрать лишний проход UTF-8 и ускорить JSON — отдельная гипотеза.** Сейчас явно создаётся текстовая копия перед `json.loads`; можно отдельно сравнить разбор байтов и совместимый быстрый JSON-декодер на сохранённых ответах. Число обращений к игре не уменьшится; это оптимизация CPU и временной памяти. Требуется проверка эквивалентности типов/чисел и обработки повреждённого ответа. Источник исходного расхода — те же строки decode выше.
4. **Разделить загрузку и запись — обоснованная архитектурная гипотеза, не новая возможность API.** Несколько сетевых работников → ограниченная очередь → один последовательный обработчик SQLite могут перекрыть ожидание сети и запись, ограничить память и уменьшить конкуренцию записей. Возможный результат определяется нашими измерениями. Поддержка HTTPX/Comlink сама по себе этого не доказывает.
5. **Раскладывать игроков по времени вместо общего залпа — другая цель.** Это может сгладить пики и уменьшить ожидание других фоновых работ; суммарное число запросов за тот же период не сокращается. Сохранение часового срока свежести требует отслеживать срок каждого игрока и догонять пропущенное после перезапуска.

## Что не считать надёжной оптимизацией без отдельного контракта

Не выводить неизменность персонажей/модулей только из общего ГМ, времени последней активности или полей гильдейского профиля. Для `/player` не документирован маркер версии ростера, по которому можно доказать отсутствие изменений. Сравнение/хеширование уже полученного полного ростера может сократить работу с БД, но не сам сетевой запрос. [Состав данных игрока](https://github.com/swgoh-utils/swgoh-comlink/wiki/Player-Data), [параметры `/player`](https://github.com/swgoh-utils/swgoh-comlink/wiki/Getting-Started#player).

## Отдельно: allyCode против playerId

Подтверждения, что `/player` по аликоду делает дополнительный upstream-запрос по сравнению с `playerId`, в рассмотренных первичных источниках не найдено. Python-обёртка лишь кладёт один из идентификаторов в payload и выполняет один POST на `/player`; дополнительных сетевых вызовов для разрешения аликода на этом уровне нет. Внутреннее поведение сервиса Comlink из этого не следует: его реализация не опубликована, а FAQ прямо отказывает в доступе к исходнику. Поэтому «playerId уменьшает число обращений к игре» нельзя выдавать за установленный факт. Можно отдельно измерить задержку двух вариантов, но различие времени само по себе не докажет число upstream-вызовов. [Payload](https://github.com/swgoh-utils/comlink-python/blob/796cd33c06c5e2ccf932f3a9d3883d3d50f2d5ca/src/swgoh_comlink/_base.py#L307), [один вызов `_post`](https://github.com/swgoh-utils/comlink-python/blob/796cd33c06c5e2ccf932f3a9d3883d3d50f2d5ca/src/swgoh_comlink/swgoh_comlink.py#L415), [FAQ об исходнике](https://github.com/swgoh-utils/swgoh-comlink/wiki/FAQ#q-can-i-get-access-to-the-source).
